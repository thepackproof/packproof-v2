## Proposed resources

`distribution.yaml` creates exactly these ten resources:

| Logical resource | Type | Purpose |
|---|---|---|
| ReleaseBucket | S3 bucket | New private, encrypted, versioned release storage; retained on deletion/replacement |
| OriginAccess | CloudFront origin access control | SigV4-sign every request to the private S3 origin |
| ArtifactCache | CloudFront cache policy | Honor binary cache headers; minimum TTL zero |
| UncachedMetadata | CloudFront cache policy | No caching of updater pointers and health response |
| DownloadHeaders | CloudFront response headers policy | HTTPS security headers for downloads |
| MetadataHeaders | CloudFront response headers policy | Security headers plus `no-cache,no-store,must-revalidate` |
| Distribution | CloudFront distribution | Separate `downloads.thepackproof.com` delivery endpoint |

| StagingPublisher | IAM role | Exact GitHub repository, main branch, staging publish environment, staging S3 prefix |
| ProductionPublisher | IAM role | Exact GitHub repository, main branch, production publish environment, production S3 prefix |

Physical bucket and role names are generated by CloudFormation. There are no changes to existing stacks, DNS, certificates, distributions, roles, or application services. The template has no Route 53 resources and cannot change external DNS.

Publisher roles allow only `s3:ListBucket` with their own channel prefix and `GetObject`, `PutObject`, `AbortMultipartUpload`, and `ListMultipartUploadParts` on objects beneath that prefix. They cannot delete objects or versions, modify bucket policies, alter IAM, change DNS/CDN settings, read signing credentials, or change `desktop/health.json`. Resource permissions were validated against IAM Access Analyzer.

The trust policy requires all of: exact repository/environment `sub`, audience `sts.amazonaws.com`, `ref=refs/heads/main`, immutable `repository_id=1349680833`, and immutable `repository_owner_id=314726215`. Both the standard repository subject and the exact immutable repository subject already present in this account's existing deploy trust are allowed; the additional immutable-ID conditions prevent a reused repository or organization name from acquiring access. There are no organization, repository, branch, or environment wildcards.

## Bootstrap and verify readiness

Use an infrastructure operator session, not either restricted publish role, to upload the checked-in `health.json`. Set `DESKTOP_RELEASE_BUCKET` to the exact `ReleaseBucketName` output:

```bash
aws s3api put-object --region us-east-1 \
  --bucket "$DESKTOP_RELEASE_BUCKET" --key desktop/health.json \
  --body infra/desktop-distribution/health.json \
  --content-type application/json \
  --cache-control 'no-cache,no-store,must-revalidate'
curl --fail --silent --show-error --proto '=https' \
  https://downloads.thepackproof.com/desktop/health.json
curl --head --fail --silent --show-error --proto '=https' \
  https://downloads.thepackproof.com/desktop/health.json
```

The body must contain `"service":"packproof-desktop-updates"`; headers must include `Cache-Control: no-cache,no-store,must-revalidate` and `X-PackProof-Distribution: desktop-updates-v1`. Confirm the TLS certificate matches the download domain, no redirect occurs, and anonymous access to the S3 object URL is denied. Do not fabricate `latest.yml` or point clients at a development/unsigned artifact just to test readiness.

The bucket is private; downloads through CloudFront are intentionally public. OAC authenticates CloudFront's origin request. It does not sign application binaries or replace Authenticode, Developer ID, notarization, updater hash verification, or protected release gates.

## Connect the signed release workflow

For `desktop-staging-publish` and `desktop-production-publish`, configure:

| GitHub environment variable | Value |
|---|---|
| PACKPROOF_RELEASE_BUCKET | `ReleaseBucketName` stack output |
| PACKPROOF_RELEASE_ROLE_ARN | Matching staging or production role ARN output |
| PACKPROOF_RELEASE_AWS_REGION | `us-east-1` |
| PACKPROOF_RELEASE_ACCEPTANCE_JSON | Production only: actual required acceptance evidence for the exact source commit |

Require `main` as the deployment branch in both environments. Production should require review and prevent self-approval. Keep signing certificates and notarization credentials in the separate existing `desktop-staging` / `desktop-production` build environments. Do not place signing material in the publish environment or S3 bucket.

The workflow already grants OIDC only to its publish job. Test staging first. The publisher validates signed evidence and all three architecture artifacts before cloud writes, uploads binaries first, and promotes updater metadata last. It checks an exact S3 key through a prefix-restricted list before HEAD, so a missing object is not confused with a denied request. Release roles need no broad bucket listing or CloudFront invalidation permission.

Paths are fixed:

```text
desktop/staging/win32/x64/
desktop/staging/darwin/x64/
desktop/staging/darwin/arm64/
desktop/production/win32/x64/
desktop/production/darwin/x64/
desktop/production/darwin/arm64/
desktop/health.json
```

Versioned artifacts get immutable cache headers. `latest.yml` / `latest-mac.yml` always bypass the CDN cache. Range requests remain supported for resumable/differential downloads. Existing artifact versions remain available during rollout; the bucket lifecycle only aborts incomplete multipart uploads after seven days, with no expiry of current releases or old object versions.

## Recovery

The S3 bucket is retained if the stack is deleted or replaced. Do not empty it to force stack deletion. An update rollback should be a new properly signed version; if an emergency metadata restoration is necessary, an infrastructure operator can recover a known-good version from S3 version history after rechecking signature/hash evidence. Publish roles intentionally have no version-delete or arbitrary version-restore privileges.

Before changing the template after deployment, use an UPDATE change set for this stack and review its exact resource impact. Never repurpose the existing website stack or distribution for desktop release hosting.
