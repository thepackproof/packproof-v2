# Isolated deployed runtime acceptance

These templates target only the approved synthetic foundation in account `784514617543`, `us-east-1`, VPC `vpc-0c4f12c0ba9393ae3`. They are not a production deployment template or an independent release approval.

`runtime-assets.json` owns the private egress, build project, immutable ECR repository, cluster, separate task/execution roles, injected configuration secrets and regional management-event audit trail. `runtime-services.json` owns separate API and worker Fargate services. Regenerate both with `node backend/scripts/generate-isolated-runtime-infra.mjs` and validate every template with cfn-lint before applying a reviewed CloudFormation change set.

The tasks use the same exact image digest but different ECS-only workload roles and PostgreSQL logins. Neither application role can read the database-owner secret or administer IAM, keys or retention. The API cannot write or read the recovery journal or sign its receipts. The worker cannot sign root Proof manifests or delete protected versions. Execution roles pull the image, write logs and inject only their respective database password plus required shared configuration. The bootstrap owner secret exists only in the temporary build environment.

The API exposes TLS port 3443 only to the isolated runner security group. A seven-day test certificate for `packproof-m1.test` is verified against its separately pinned public certificate; hostname and certificate verification remain enabled. No public IP, public listener, DNS record or production identity pool is used. The application still listens on container-local port 3000. HTTP requests are streamed through the TLS wrapper without changing the canonical capture services.

Application processes run as UID 1000 with a read-only root filesystem. Fargate creates an empty bind volume root-owned; a short initializer changes only that temporary volume to mode 1777 before either application starts. This permits bounded media validation and the public protection-evidence file without granting the application root privileges.

## Execution order

The first bootstrap creates `m1_service_20261021`, applies the existing migrations and runtime grants, generates separate credentials and shared keys in Secrets Manager, and builds the exact candidate image. 2. Resolve the pushed image's digest and inspect its scan results. Create task definitions with `DesiredCount=0`. Run `isolated-runtime-role-probe.mjs` in separate API and worker tasks using those task roles. Before a repeated probe, reset the public fence marker to a different source value so an old marker cannot satisfy the new run.
3. After both probes report their initial checks, set the assets stack's `WriterFence=CLOSED` through CloudFormation. When the update completes, write the current image source SHA to `acceptance/runtime/config/fence-now.json`. 5. With services still stopped, run `RUNTIME_PHASE=control`, `RUNTIME_CONTROL=protect`. This enables the dedicated logins and aligns the database durability policy and writer generation. Wait for both new task revisions to be healthy before rerunning acceptance; record failed attempts as well as the successful run.

## Pausing and resuming

After acceptance and evidence collection, set the services' `DesiredCount=0` and wait for both tasks to stop. Run the owner-only controller with `RUNTIME_CONTROL=close`: it fences database writes, sets both dedicated logins to NOLOGIN and terminates their sessions. Then apply `WriterFence=CLOSED` and `ComputeEnabled=false` to the assets stack. This removes temporary CodeBuild/egress resources and stops this test trail's delivery while retaining the image, public/private evidence, secrets, database, task-role policies and logs. The account's normal CloudTrail event history is unaffected.

To resume, keep services stopped while recreating temporary compute, refreshing expired TLS/protection/trust evidence, rerunning current role/fence probes and enabling the dedicated logins through the owner controller. Continue the existing recovery journal sequence; do not bootstrap a new database against the same journal root or reuse expired evidence. Test credentials are environment-scoped and must not be copied into another deployment.
