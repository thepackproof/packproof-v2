# ProofWitness R&D (F09)

Private laboratory protocol, not a deployed public transparency service. Independent operators: **0**. Local test signatures must never be described as independent witnessing.

## Design and interoperability boundary

`witness.py` uses maintained `pymerkle==6.1.0` for SQLite Merkle storage, RFC6962 SHA-256 domain-separated hashing, tree construction, inclusion and consistency proofs. It does not introduce a new Merkle algorithm. The proof **encoding** is pymerkle JSON, rather than Tessera tiles or transparency.dev signed-note wire format; an external operator needs a reviewed compatible adapter. Transparency.dev Merkle/Tessera/witness were evaluated from primary documentation; the local Python runtime and standard-library integration were selected for this isolated prototype. Production selection/interoperability remains a review gate.

The leaf input is `SHA256("packproof.witness.commitment.v1\\0" || 32-byte blind || 32-byte canonical-record-digest)` as raw 32 bytes. RFC6962 leaf hashing adds the library's 0x00 prefix. Only this blinded commitment goes into the log. Order IDs, tracking numbers, account identifiers, raw record digests, media or URLs are not stored. Opening material remains in authorized private receipts. Timing and volume leakage remain.

A JSON/RFC8785 checkpoint contains origin, tree size, root hash, RFC6962 SHA-256 algorithm and issued-at time, signed with Ed25519. Witnesses validate log trust, read their durable previous checkpoint, require a real consistency proof before advancing, reject same-size split views and rollback, and append their accepted checkpoint to persistent history. A log signature is not a witness signature. SQLite and process locks give idempotent commitment insertion; committed receipts survive restarts. The backend owns durable outbox and retry scheduling; outages never block ordinary proof finalization.

The library's general proof verifier accepts flexible paths. This adapter additionally validates exact path/rule/subset/size/index shapes generated by the pinned library with dummy nodes, then verifies the actual cryptographic path. Dummy nodes do not participate in integrity verification. Bounds are 100,000 leaves, SHA256 only, security domain separation required. This avoids accepting misleading claimed sizes or indices.

## Commands

```sh
python3 -m venv /tmp/packproof-privacy-venv
/tmp/packproof-privacy-venv/bin/pip install -r research/witness/requirements.lock.txt
/tmp/packproof-privacy-venv/bin/python -m unittest research.witness.test_witness -v
/tmp/packproof-privacy-venv/bin/python -m research.witness.benchmark
/tmp/packproof-privacy-venv/bin/python research/witness/witness.py append --record-digest CANONICAL-SHA256 --blind PRIVATE-32-BYTE-HEX --log-db PRIVATE-LOG.sqlite --log-key PRIVATE-LOG.pem --log-id PRIVATE-LOG-ID --policy-id PINNED-POLICY-ID
/tmp/packproof-privacy-venv/bin/python research/witness/witness.py verify-inclusion receipt.json --policy OUT-OF-BAND-TRUST.json --record-digest EXPECTED-CANONICAL-SHA256
/tmp/packproof-privacy-venv/bin/python research/witness/witness.py consistency --log-db PRIVATE-LOG.sqlite --old-size 1 --new-size 2
/tmp/packproof-privacy-venv/bin/python research/witness/witness.py checkpoint --state-db WITNESS.sqlite --log-id PRIVATE-LOG-ID --operator-id NAMED-OPERATOR
/tmp/packproof-privacy-venv/bin/python research/witness/witness.py witness receipt.json --policy OUT-OF-BAND-TRUST.json --state-db WITNESS.sqlite --key PRIVATE-WITNESS.pem --operator-id NAMED-OPERATOR --consistency-proof proof.json
/tmp/packproof-privacy-venv/bin/python verifier/rnd_verify.py research/witness/reports/synthetic-receipt.json --policy research/witness/reports/synthetic-trust.json --canonical-record research/witness/reports/synthetic-record.json
```

Persist a fresh 32-byte CSPRNG blinding value privately in the authorized outbox before the first append. Reuse it for retries of that same publication identity; never reuse across different records. Treat command arguments/process telemetry as private; don't log the opening. Store keys, state and openings outside source control with owner-only file/directory permissions and encrypted backups.

`verify-inclusion` returns `INCLUDED / LOG_INCLUSION_ONLY`; it never claims witnessing. `verify` and `verifier/rnd_verify.py` require both named operators from the externally pinned policy. Test-controlled keys yield `TEST_WITNESSED`, independentOperatorCount=0. `--require-independent` requires both policy entries to be specifically named, independent, non-test operators. Operator independence is a governance assertion in the out-of-band trust policy; cryptography cannot determine organizational independence.

The isolated backend accepts optional `PACKPROOF_RND_WITNESS_OPERATORS` JSON containing exactly two `{operatorId,keyFile,stateDb}` entries. Those local private keys are allowed only when both pinned policy entries are explicitly `testOnly:true, independent:false`, with a test-only policy. The durable job reads each operator's last accepted checkpoint, obtains and verifies real consistency proofs, collects both signatures and verifies the completed receipt before appending the result. Failure of either operator fails/retries the publication job; it cannot silently fall back to a witnessed status. Without configured operators, the result remains log inclusion only. Restarts retain each operator's checkpoint database, and retry uses the job's original blinded commitment. This adapter intentionally cannot claim independent operators from centrally configured private keys.

Offline verification needs public keys and receipt opening, not account access, a service secret or a PackProof login. It reports checkpoint age and the exact record checked. It does not imply complete transaction history, current log freshness, future extensions or truth of source media. The synthetic fixture trust file is only for its accompanying synthetic record.

## Trust policy and key operations

See `reports/synthetic-trust.json` for the versioned structure: policy ID, log ID, log keys, witness keys and exactly two required operator identities. `logKeys`/`witnessKeys` are keyed by SHA-256 of raw Ed25519 public-key bytes; entries contain the PEM public key, operator identity, `testOnly`, `independent`, optional UTC `validFrom`/`validUntil` and `revoked`. Keep the trust policy in an independently authenticated registry; never accept an export's self-selected trust as authority.

1. Onboard each real external organization through a separate key exchange and operational agreement; confirm named operator, independent control, checkpoint retention, freshness targets and incident contact. Both signatures are mandatory. Current outside-operator count stays zero until this occurs.
2. Pin initial checkpoint and public keys; archive every accepted checkpoint. Start each operator with its own access-controlled persistent database. Never share signing private keys across organizations.
3. Rotate by publishing a reviewed policy version with explicit new key IDs and validity windows before use. Retain old public keys/checkpoints for historical verification. Revocation in the applicable trust policy blocks the revoked signer; do not silently replace a trusted key from a receipt.
4. On split view, invalid consistency, unexpected key, rollback or corrupt state, stop advancing and alert. Preserve conflicting signed checkpoints as evidence. Do not reset/delete prior state to make the new log pass.
5. Restore log and witness databases from separately backed-up consistent snapshots, then verify consistency from the last externally retained checkpoint before signing or publishing again. If the checkpoint cannot be reproduced, fail closed and investigate. Local tests exercise restart persistence, missing consistency, split views, rollback and unknown/revoked keys.
6. Publication failures retry with the original persisted commitment identity and bounded attempts. Monitor oldest queued age, inclusion age, both witness lags, signature errors, consistency errors and duplicate retry count. Exceeding the proposed ten-minute healthy target is a publication/availability event, never an integrity success. External/network latency is unmeasured here.

## Measured scope and unresolved gates

`reports/local-synthetic-2026-10-02.json`: 32 real append/inclusion/consistency/checkpoint/test-witness rounds; local p95 end-to-end 3.22 ms and local verification p95 0.561 ms on the recorded Linux/Python host. This measures local protocol work, not network service latency. No cloud resources or external operators were used.

A real SQLite backup/restore rehearsal copies the log and each witness into fresh databases, compares retained checkpoints, advances with a consistency proof, and rejects a stale restored log without rewinding accepted history. This local rehearsal does not qualify an external operator disaster-recovery service.

Tests reject changed leaf/opening/record, malformed proof/path/security profile/tree size/index, unknown/revoked signer, missing/duplicate witness, wrong policy, inconsistent checkpoint and rollback. Shape tests cover every index and old-size combination through tree size 16. Receipt/public trust/record fixtures contain synthetic data and public keys only; private signing keys were ephemeral and are not committed.
