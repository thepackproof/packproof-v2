# Scoped support access

This module is disabled unless actual internal account IDs are configured in `PACKPROOF_SUPPORT_APPROVER_IDS` and `PACKPROOF_SUPPORT_READER_IDS`. IDs are resolved from normal verified authentication; request bodies cannot assign a role. No user, grant or role is seeded. A support reader cannot approve their own access, even when listed in both roles.

Mount `supportAccessRouter(deps)` at `/internal/support` after authentication. An approver issues `POST /grants` with an existing `proofId`, listed `supportUserId`, reviewed internal `issueReference`, substantive `reason`, stable `operationId`, absolute `expiresAt` within one hour, and scope `METADATA` or `EVIDENCE_READ`. Metadata has an empty `evidenceIds` array. Evidence scope requires one through ten explicit committed-original IDs from that Proof. Retrying an unchanged operation returns the same grant; changing its scope requires a different approval and operation ID. A request reference is an operator review record, not evidence of customer consent by itself.

`GET /grants` lists only the actor's issued or assigned grants, capped at 100. `GET /grants/:id/metadata` returns status, dates and counts without order references, addresses, participant details, raw manifests or source facts. `GET /grants/:id/evidence/:evidenceId` permits only explicitly selected committed root evidence, including bounded ranges from the exact stored original version. It does not admit stage evidence, exports, account credentials or arbitrary object keys.

Every approval, revocation, metadata read and started content read records the internal actor, grant, request correlation, issue reference and time in an append-only support audit and in the Proof activity audit. The content audit records a started access, not a guarantee all bytes were received. Audit failure prevents reading. `POST /grants/:id/revoke` requires a substantive reason and can be performed by an allowlisted approver or the assigned allowlisted reader. It appends a revocation and cannot delete the original approval or audit.

Each read checks current reader authority, expiry, revocation and the recovery-policy fence. A media stream rechecks before sending and every 64 KiB or second of additional admitted data. Network/kernel buffers may still contain bytes admitted before revocation; already delivered bytes cannot be recalled. A stream also stops at its original grant expiry. Support grants/revocations participate in the ordered policy journal so restored uncertain or stale permissions cannot silently resume access.

The module offers no participant impersonation, evidence mutation, retention disposal, billing override or quarantine command. A quarantine requiring changed disclosure must use its independently authorized safety/legal workflow, preserve the original, and append the disposition reason. Support reads do not shorten retention or bypass deletion/hold policy; unavailable source versions remain unavailable. Operational rollout still requires real named reviewers, permitted support policy, account-role verification and completed independent access review.
