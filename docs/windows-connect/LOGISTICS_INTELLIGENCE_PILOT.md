## Controls and migration

- Keep `PACKPROOF_ORDER_WORKSPACE_ENABLED` and existing organization entitlements in force. Add an enrolled site's exact `organization:environment:location` to `PACKPROOF_GUIDED_FACILITIES` for guided setup. Comma-separated values are supported. Existing approved installations retain their legacy path.
- The setup assistant also requires that scope in `PACKPROOF_SETUP_AI_FACILITIES`. Configure `PACKPROOF_SETUP_AI_PROVIDER`, `PACKPROOF_SETUP_AI_MODEL` and the server-side `PACKPROOF_SETUP_AI_KEY` through the deployment's protected configuration. The manual workflow works when consent, service or budget is unavailable. `PACKPROOF_SETUP_AI_DRAFT_CALLS` and `PACKPROOF_SETUP_AI_DAILY_CALLS` bound calls. The provider key and unmasked customer examples do not belong in qualification receipts.
- Migrations 125–129 add the local receipt clock, lookup index, access and case records, setup request ledger, export records and per-source health data, and admit collector 0.7.0 to the existing historical backfill guard. Apply the migration catalogue and reviewed runtime-role grants before deploying a client that uses these paths. `recordsMigrationInventory(129)` and the PostgreSQL restored fixture identify the matching role policy. Existing receipt times remain valid. Older receipts have an unknown first-local-observation time.
- Keep the former profile active while testing its replacement. Removing a facility from the assistant or guided-setup allowlist controls setup eligibility. To stop live capture, revoke the matching grant or pause the source using the existing control. The existing local offline window is one hour after the last good grant check. The server checks authority at upload.
- Retain the last compatible client and backend release. An original 124 image rejects the newer migration ledger. For a profile rollback, disable the affected feature and preserve accepted history on the compatible backend. To restore a prior database, restore its matching versioned object data and queue checkpoints, verify hashes, then open a pinned revision with a permitted human account. Coordinate any production database restore with a recovery point that accounts for intervening accepted receipts.

## Facility acceptance record

Record the facility and installation scope, operator roles, source commit, binary SHA-256, signer, service identity, and approved coverage. Keep original paths, credentials and customer evidence in their authorized stores. A restricted reviewer must see only permitted orders, receive a denial for a revoked original, and see omissions in a newly generated packet. Existing downloaded files are point-in-time exports.

For each source, record the number of expected and qualified feeds, manual selections, missed candidates and reasons for deferral. For each known order, record correct links divided by reviewed links, claims with an original and field locator, and any false match. Time a carton lookup, the first eligible read to its visible revision, and recovery. Count duplicate outage cases, extra revisions on replay, illegal cross-facility links, unauthorized packet items and setup-model requests during live processing. The last four counts must be zero. Keep demo measurements separate from operations.

Use an authorized pilot reporting connection to run `psql -v installation_id=... -f backend/scripts/facility-setup-metrics.sql`. Configure `PACKPROOF_SETUP_AI_INPUT_USD_PER_MILLION` and `PACKPROOF_SETUP_AI_OUTPUT_USD_PER_MILLION` for the selected model. Missing usage or price data leaves the reported cost unknown.
