# Optional platform assurance

The research application calls the actual Play Integrity Standard API, Android KeyStore challenged-key API or Apple App Attest API. The server validates a short-lived, one-use binding to an authenticated actor, Proof, capture intent and purpose. An inventory assertion also commits to SHA-256 of the **exact `clientCanonicalJson` UTF-8 bytes** signed by the capture session key. An App Attest key and the session media-signing key are different keys.

Only `VALIDATED` platform results for that exact inventory can appear as `APP_REQUEST_VALIDATED` in a signed capture receipt. This establishes app/request assurance within the configured policy. It does not establish camera sensor provenance, physical package identity or scene truth. The original capture profile remains `FINAL_FILE_ONLY`. Successfully uploaded native sidecars receive separate immutable receipts bound to the original signed inventory; unreceived commitments remain explicitly unreceived.

## Local policy

Platform verification is disabled when no server-side policy is configured. Enable it only in the isolated research backend with `PACKPROOF_ENV=research`, `PACKPROOF_RND_ENABLED=1`, the kill switch off and the Verified Capture collection flag enabled. Explicit current experimental consent is required. Customer display remains disabled.

Set `PACKPROOF_RND_PLATFORM_POLICY_FILE` to an operator-controlled JSON file with schema `packproof.platform-policy.v1`. A shape-only template is in `config/rnd/platform-policy.example.json`; it deliberately contains no trusted root or app signing certificate. Do not turn test fixture roots into trusted Apple roots. Obtain and review authentic provider roots and app identity from the provider's official documentation and your isolated research developer account. Renew the explicit policy expiry before it lapses.

For Apple, configure the exact `TEAMID.com.packproof.mobile.research` App ID, `development` environment, trusted PEM certificates, a unique `trustPolicyId`, epoch-millisecond `trustPolicyExpiresAt`, category `3`, and exact approved bundle versions. Missing roots, an expired policy or an unqualified legacy extension format returns `UNSUPPORTED`. A changed policy ID requires a newly registered key. Legacy acceptance, if separately qualified, is an explicit `allowLegacyWithoutExtensions` policy; it is never inferred from missing evidence. Revoked key IDs are rejected.

For Android, configure `com.packproof.mobile.research`, exact base64url SHA-256 signing-certificate pins, a minimum decimal version code, required device verdicts, licensing policy and bounded maximum token age. A Google-approved application/Cloud project and authorized service-account access are external prerequisites. Set `PACKPROOF_RND_GOOGLE_ACCESS_TOKEN_FILE` to an owner-only regular file containing an OAuth access token provisioned and refreshed by the isolated credential provider. The server reads this file for each decode request. It never accepts client-decoded verdicts. It sends the opaque token only to the fixed Google Play Integrity decode endpoint using Bearer authentication, redirect rejection, timeout and response-size bounds. Missing credentials or provider failure returns `UNSUPPORTED`; provider-rejected evidence returns `INVALID`. Do not put credentials in Git or policy JSON.

## Protocol

1. Create a normal research capture intent and bind a capture start. Apple key registration may occur before the bound start.
2. POST `/proofs/:id/rnd/platform-challenges` with `{intentId,purpose:"REGISTER_KEY"}` for initial Apple enrollment, or `{intentId,purpose:"CLOSE_INVENTORY",inventoryDigest}` for final inventory. Supply an `Idempotency-Key`. Online intents only; no more than eight challenges per purpose per intent.
3. Use the returned `expectedClientDataHash` (standard base64) for App Attest, or `requestHash` (base64url) for Play Integrity. Both encode the SHA-256 digest of the server-signed challenge canonical bytes. Challenges expire after two minutes.
4. POST `/proofs/:id/rnd/platform-challenges/:challengeId/verify`, with a distinct stable idempotency key. Play Integrity body: `{platform:"android",token}`. Challenged Android key body: `{platform:"android",certificateChainBase64,publicKeyPem,clientCanonicalJson,inventorySignatureBase64}`; it requires its own `CLOSE_INVENTORY` challenge and cannot be mixed with a token. Apple enrollment: `{platform:"ios",keyId,attestationObjectBase64}`. Apple inventory: `{platform:"ios",keyId,assertionObjectBase64}`.
5. Close the research capture intent using the exact signed client inventory. The server attaches only matching validated platform receipts before it seals the capture receipt. Ordinary recording, uploading and Proof completion remain independent of optional attestation success.

Challenges and results are immutable. Repeating the same evidence returns the same record; different evidence cannot consume an already-used challenge. Apple key IDs cannot be reassigned to another actor or reset. Assertion signatures, app identity and monotonically increasing counters are checked, and the counter compare-and-swap and signed result are committed in one database transaction. Evidence is rejected after the capture receipt is sealed.

## Verification and limits

`backend/tests/rnd-platform-assurance.test.ts` checks certificate chains, nonce/app/key/environment bindings, signatures, counters, malformed CBOR, provider identity, version, time and revocation boundaries. `backend/tests/rnd-platform-service.test.ts` exercises immutable database records, actor isolation, challenge expiration, HTTP authentication, kill switch, real generated X.509/ECDSA fixtures, and persistent counters. Generated roots and injected Google responses are protocol fixtures, not device qualification evidence.

The Android challenged-key verifier applies an explicit `androidKey` policy after chain signatures and revocation verification. Its strict KeyMint 100/200/300/400/500 profile requires the server challenge, exact attested P-256 public key, signing purpose, SHA-256 digest, generated key origin, allowed hardware security levels, locked verified boot, app package/version/certificate pins and explicit OS/vendor/boot patch floors. It selects the root-most attestation extension and checks adjacent provisioning information when present. An ancestor's attestation is never applied to a descendant key. Delegated keys, legacy Keymaster profiles, expired factory certificates and unknown authorization tags fail closed; this is a deliberately narrow supported profile, not an unreviewed compatibility exception.

Use `config/rnd/android-key-policy.example.json` as a policy shape only; supply authentic current root PEMs, reviewed application certificate pins, a unique policy ID, future epoch-millisecond policy/revocation expiry, and an authentic revocation snapshot's `entries`. Obtain roots and the revocation snapshot from the official Android endpoints over authenticated HTTPS through the operator's configuration process. Treat `revocationValidUntil` as the snapshot freshness bound from its cache policy, never an invented long-lived guarantee. The server does not fetch trust roots from client evidence and does not silently refresh trust. Expired or missing roots, policy or revocation data yields `UNSUPPORTED`. Restart the isolated backend when replacing its operator-controlled policy. Set `EXPO_PUBLIC_PACKPROOF_RND_KEY_ATTESTATION=true` only for the research build to request native evidence; absence keeps this adapter disabled.

The native adapter makes a separate short-lived AndroidKeyStore key with the 32-byte `expectedClientDataHash` as its attestation challenge, signs the exact canonical inventory using SHA256withECDSA, obtains its certificate chain, then deletes the temporary key. The server verifies the inventory digest and possession signature in addition to the certificate policy. Its signed result labels the key role `ATTESTATION_REQUEST_KEY`, `qualification: RESEARCH_UNQUALIFIED`, and the recording-session key `NOT_CHECKED`. The earlier capture session key remains `UNKNOWN`; successful request-key attestation cannot upgrade it. No hardware-protected key claim is enabled by chain validity alone.

`backend/tests/rnd-android-key-policy.test.ts` checks generated current-format certificates, policy downgrade rejection, root-most extension attacks, provisioning, malformed ASN.1, root/revocation expiry, app and key binding, exact inventory signatures, one-use persistence and replay. These fixtures contain no Google-signed device evidence.

Physical iOS/Android qualification, real provider credentials and signing identities, platform security review, current root/revocation governance and per-device performance budgets remain external gates. No production credential was used and no provider network call was made by these tests.
