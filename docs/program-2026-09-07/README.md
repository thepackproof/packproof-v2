# September 7 program operating toolkit

This directory makes W13–W18 executable and reviewable without inventing customers, payments, legal advice, release evidence or elapsed cohorts. The attached plan's 65 lettered acceptance criteria are preserved verbatim in the acceptance register. W17's six expansion decisions have explicit triggers, first slices and test gates.

The implementation includes a deterministic weekly report engine, privacy-safe input validation, event/usage deduplication, a persistent finalized-Proof usage ledger and a verified-provider accounting seam. An empty input produces unknown rates and contribution. No priced offer, subscription, invoice, provider verifier or actual charge is enabled by default.

## Run the weekly decision report

From `backend/` after installing the repository dependencies:

```bash
node --import tsx src/analytics/weekly-report-cli.ts --input ../docs/program-2026-09-07/observations.empty.v1.json --json ../docs/program-2026-09-07/weekly-report.synthetic.json --markdown ../docs/program-2026-09-07/weekly-report.synthetic.md
node --import tsx src/analytics/weekly-report-cli.ts --schema
npx vitest run tests/program-metrics.test.ts tests/program-metrics-billing.test.ts
```

For production builds, the same entry point is `node dist/analytics/weekly-report-cli.js`. The CLI reads one bounded local JSON file, validates every field before creating outputs, and makes no network or billing calls. It rejects unknown fields, raw identifiers, malformed dates, contradictory observations and changed facts under a reused logical ID. `--help` describes its options. The checked-in reports are **synthetic zero-observation examples**, not an operating readout.

Copy the empty input to an access-controlled operating location. Use `observations.schema.v1.json` for field structure and `metric-dictionary.v1.json` for the meaning of each field and denominator. Source references use `pr_` plus 32 hexadecimal characters, generated by the keyed helper; do not enter names, email, addresses, video, declaration text, tokens or arbitrary notes. Dates use UTC milliseconds. Report and cost periods end exclusively. `asOf` fixes the observation cutoff, so rerunning the same input returns the same report.

The dictionary is implemented but still needs an accountable operating freeze before enrollment. The script cannot prove that submitted observations are complete or authentic. An operator must reconcile them to their governed source register, including eligible orders, excluded devices, failed exports, dropouts, payments, invoices and all assistance. Keep identifiable consent/contact records outside this repository.

## What the report calculates

- First-use activation, eligible-order coverage and the third cohort week as separate denominators.
- Durable upload commitment within an elapsed 24-hour window; cancellations and failures remain included. All-started completion, late commitments, offline time and pending durability are separate diagnostics.
- Reviewer technical acceptance, checklist completeness and comprehension separately. Failed/incomplete tasks remain counted; missing preparation or effort timings prevent a passing timing gate.
- Paired added hands-on effort, median/p90 and unattended time; preparation-time improvement with raw task counts.
- Actual paid continuation with dropouts retained, and separately elapsed second-period payment and use.
- Support minutes including founder help, plus variable/support contribution, infrastructure gross margin and fixed/capacity-step costs. Every cost category needs actual source evidence, the billing period must elapse and the operator must record a zero unexplained reconciliation difference before contribution appears.

A zero denominator is `null`/unknown. A starting threshold is not automatic G1–G4 approval, statistical certainty, marketplace acceptance or causal fraud reduction. The report recommends the plan's corrective action sequence when usable data show reliability, coverage, payment, reviewer or contribution problems. It otherwise asks for the remaining evidence.

## Application integration seams

`backend/src/analytics/contracts.ts` exports:

| Function | Trusted caller responsibility |
|---|---|
| `pseudonymizeReference(key, namespace, identifier)` | Use a dedicated managed analytics key of at least 32 bytes. Register the key version for a cohort; do not silently rotate all identities mid-cohort. |
| `validateProgramEvent(value)` | Project only allowlisted fields from canonical server outcomes or verified provider events. A client-supplied `authority` property is not authorization. |
| `deduplicateProgramEvents(events)` | Reuse the operation ID and original occurrence time across retries. Proof finalization, preservation, export approval and payment facts deduplicate by scoped subject. Changed facts conflict. |
| `reconcileFinalizedProofUsage(rows)` | Supply one genuinely durable finalization receipt per Proof. This pure contract demonstrates stable logical billing identity; the persistent ledger below performs actual storage dedupe. |
| `buildWeeklyReport(input)` | Reconcile governed source observations; use manual, consented quality checks for “usable Proof,” which is stronger than a finalized DB status. |

Authoritative event names are `upload.intent`, `evidence.committed_pending_durability`, `preservation.completed`, `proof.finalized`, `export.approved`, and `payment.settled`. `capture.interaction` is client-authored timing context. Successful preservation/finalization events must be emitted only after the corresponding durable receipt; a successful upload or DB transaction cannot stand in for preservation. The toolkit does not silently wire itself into API events.

## Persistent billing and allowance boundary

Migration `042_billing_usage.sql` adds immutable offer versions, consented account periods, one usage row per transaction Proof, provider/customer bindings, verified event records and payment/refund ledger entries. It seeds no offers. Backend functions are in `backend/src/billing/usage-ledger.ts`:

| Function | Behavior |
|---|---|
| `registerOfferVersion(db, clock, definition)` | Internal configuration command. Same version/same terms is a replay; changed terms require a new version. Approved pricing requires an approval reference and complete limits. Every offer shares `canonical-original-v1` preservation. |
| `scheduleApprovedOfferPeriod(db, clock, input)` | Internal consented enrollment command. Rejects drafts, overlapping periods and retroactive new terms. A record accepted without an offer remains unpriced. |
| `reconcileDurableFinalizedUsage(db, clock, {limit: 100})` | Bounded scheduled worker, independent of HTTP visits. Locks candidate records, requires the canonical seller and a matching durable finalization receipt, then inserts one immutable logical unit. Retried finalizations do not add units. |
| `getAccountUsageSummary(db, clock, authenticatedUserId, window?)` | Own-account read. Shows finalized, durability-confirmed and ledger-metered counts separately; active consented allowance; sandbox/live payment totals separately. It does not reserve upload bytes or revoke historical access. |
| `bindBillingCustomer(db, clock, binding)` | Internal mapping after authenticated provider linking. Provider/environment/account/customer identity cannot be reassigned to a different PackProof user. |
| `ingestVerifiedBillingEvent(db, clock, verifier, payload)` | Requires a provider-specific verifier before database accounting. The verifier must check the provider's actual signature or authenticated refetch, freshness and configured provider account. No disabled verification fallback exists. |

Mount the usage read only behind existing authenticated-user middleware. Schedule reconciliation in the existing durable worker runtime; do not make useful progress depend on visiting `/me/usage`. The allowance read is **not** admission control: use W03's atomic reservations to enforce concurrent new-capture quotas. Consumed or expired allowances must never control retrieval, participant rights, exports or preservation. Supplements incur no automatic extra charge in this slice.

Provider event normalization uses opaque references and monetary facts only. It excludes raw webhook bodies and personal billing details. The normalized occurrence timestamp identifies the underlying settled payment/refund, not delivery of a later webhook. Replayed source IDs with changed facts conflict; different notifications of the same payment produce one ledger entry. Distinct refunds require distinct refund references. Provider environment and account are part of every key. There is no provider charge call, invoice generation or actual subscription cancellation adapter in this module.

The approval references and provider verifier are internal integration requirements, not evidence that legal or provider approval already occurred. Actual provider configuration, payment, invoice reconciliation, cancellation handling and a full real billing period remain W13 operating gates.

Preserve the distinction between implemented, verified, released and observed.
