# Optional Stripe accounting and customer service adapter

This implementation does not select Stripe for the business, publish an offer, create charges/invoices, cancel a subscription, or assert any actual payment. It is disabled when `PACKPROOF_BILLING_PROVIDER` is absent. Existing immutable offer consent and historical evidence access remain independent.

`stripeBillingConfigFromEnv` requires explicit provider `stripe`, `PACKPROOF_STRIPE_ACCOUNT`, `PACKPROOF_STRIPE_ENVIRONMENT` (`sandbox` or `live`), `PACKPROOF_STRIPE_API_VERSION`, `PACKPROOF_STRIPE_ACCOUNT_MODE` (`direct` or `connected`), and `PACKPROOF_STRIPE_CREDENTIAL_REFERENCE`. Partial configuration fails closed. Credentials resolve through `IntegrationCredentialStore` with adapter key `stripe-billing`; managed material contains `apiKey` and `webhookSecret`. Environment-specific secret/restricted-key prefixes are enforced. No key value belongs in configuration snapshots or logs.

`StripeBillingAdapter` implements `BillingProviderVerifier`. Pass unchanged `Buffer` body bytes and the `Stripe-Signature` header into `ingestVerifiedBillingEvent`. The dedicated webhook route must precede JSON parsing, use a one-MiB raw-body cap, and return only after verified accounting is committed; failures remain retryable rather than acknowledged as complete. The adapter verifies documented v1 HMAC using constant-time comparison and a five-minute timestamp window, including rotating signatures, before parsing or requesting provider data. It requires the configured API version, event environment, and direct/connected account scope. Organization/thin event contexts are unsupported and rejected. These requirements follow Stripe's [webhook verification procedure](https://docs.stripe.com/webhooks) and [event context definition](https://docs.stripe.com/api/events/object).

Supported accounting events are `payment_intent.succeeded`, immediately succeeded `refund.created`, and `refund.updated`. Failed/canceled refund events (`refund.failed` or `refund.updated`) additionally verify the failure balance transaction and append a positive `refund_reversed` leg; the original negative refund remains unchanged. See Stripe's [refund lifecycle and event guidance](https://docs.stripe.com/refunds). Other events do not create accounting entries. The adapter authenticates `/v1/account`, refetches the payment/refund, charge and balance transaction, and checks account, customer, currency, amount and financial-source relationships. USD only is intentional. Missing customers, missing financial objects, pending refunds without an acknowledged succeeded financial leg, foreign currency or inconsistent facts fail closed. Webhook metadata cannot bind a PackProof user. An existing internal provider/customer binding is mandatory. See the official [PaymentIntent](https://docs.stripe.com/api/payment_intents/object), [refund](https://docs.stripe.com/api/refunds/object) and [charge](https://docs.stripe.com/api/charges/object) object contracts.

The normalized occurrence time is the immutable balance-transaction creation time, so redelivery or another notification of the same financial object cannot move the ledger between periods. This is provider balance-booking time, not bank payout, invoice period, dispute resolution, or the time funds become available. Reconciliation must retain those distinctions; Stripe defines `created` and `available_on` separately in its [balance transaction contract](https://docs.stripe.com/api/balance_transactions/object). PaymentIntent and refund IDs form separate immutable logical units, so partial refunds remain distinct. Migration `046_billing_refund_reversals.sql` requires a matching original refund debit before its reversal. Reordered reversal notifications fail with retryable reconciliation-required status until the historical debit is recorded. A signed historical succeeded-refund event can still be reconciled against its original balance debit after the provider reports failure. A refund that never had an accepted succeeded debit requires explicit reconciliation; this limited adapter never invents the missing financial leg. Account summaries explicitly remain unreconciled. No entitlement or new invoice is inferred from a webhook.

`listOwnInvoices(db, authenticatedUserId, {customerReference?, startingAfter?})` resolves only persisted own-account bindings, fetches at most 100 invoices per page, and returns identifier/status/amount/time fields without addresses, email, URLs or arbitrary provider text. Pagination remains explicit. It does not create or edit invoices. This uses Stripe's [invoice listing endpoint](https://docs.stripe.com/api/invoices/list).

`createOwnCancellationPortal(db, authenticatedUserId, {customerReference?, subscriptionReference, operationId})` is additionally disabled unless `PACKPROOF_STRIPE_CANCELLATION_PORTAL_ENABLED=true`, `PACKPROOF_STRIPE_PORTAL_CONFIGURATION`, and fixed HTTPS `PACKPROOF_STRIPE_PORTAL_RETURN_URL` are supplied. Invoke only for an explicit signed-in user action. It verifies subscription/customer ownership, creates a hosted cancellation-review flow with a stable account/customer/subscription/operation idempotency key, and accepts only `https://billing.stripe.com` response URLs. The returned state says cancellation has **not** yet completed. The customer still reviews and confirms at Stripe. Source: [portal session and cancellation flow contract](https://docs.stripe.com/api/customer_portal/sessions/create).

Every provider request targets a fixed Stripe origin, rejects redirects, uses the explicit API version and account context, has an eight-second abort budget and streams at most one MiB of response data. Provider errors never echo response bodies or secrets. A webhook can require several bounded verification reads; provider outages return failure for redelivery, and ledger idempotency handles lost responses. A production queue/outbox can be added if measured delivery latency requires it, preserving verified raw-event evidence and its freshness semantics.

Before activation: choose the provider/account, scope billing to PackProof's approved offers (use a dedicated account or implement explicit product/invoice association), approve terms and retention commitments, bind customers through authenticated onboarding, configure the matching webhook API version/events and least-privileged managed secret, and exercise real provider sandbox delivery, invoice, refund and cancellation paths. Then reconcile a real billing period. A portal return URL never proves completed cancellation; add verified subscription-state reconciliation before using cancellation in entitlement/account status. Neither cancellation nor allowance exhaustion may revoke past evidence access.

Current verification: twelve synthetic provider/real-PGlite tests pass in `backend/tests/program-metrics-stripe.test.ts`; all HTTP responses in these tests are local fixtures. No Stripe API call, money movement or active subscription was performed during implementation.

## Daily reconciliation and paid-publication gates

`processStripeBillingReconciliation(db, clock, adapter, {initialStartAt, maxEventsPerRun?})` is the optional worker seam. Schedule it independently of HTTP when billing and an explicit `PACKPROOF_STRIPE_RECONCILIATION_START_AT` are configured. It processes one page of at most 100 event references and ten accounting events per tick by default; additional ticks continue the persisted cursor. A database lease prevents active workers from taking the same scan, while ledger idempotency safely handles an expired lease or lost completion response. Separate durable event rows let an earlier refund debit be processed before retrying a reordered reversal; no private event body is stored.

Each completed day closes at UTC midnight and the next scan overlaps the preceding two days. The first baseline must be explicit and cannot silently move. Stripe's [event listing API](https://docs.stripe.com/api/events/list) and [event retrieval API](https://docs.stripe.com/api/events/retrieve) expose only the previous 30 days, so missing history beyond that window blocks the scan instead of claiming full reconciliation. Old source-event API versions are preserved by Stripe and must match the configured contract. Unbound customers, unsupported financial records, provider failures and exhausted attempts remain visible; twelve failed event attempts become terminal. Never-settled snapshot events are retained as ignored, not counted as money. Reversal ordering does not exhaust its attempts while waiting for the original debit. `getStripeBillingReconciliationStatus` exposes aggregate pending/failed/gap status for operational review.

A complete provider scan proves coverage only from its explicit baseline; it does not prove invoice, product scope, bank payout, customer cancellation, cost or margin reconciliation. Account financial summaries remain `unreconciled`. An operator must inspect blocked scans and reconcile missing/provider-specific facts; altering the baseline or dropping failed events is not a valid repair. Five synthetic database tests cover bounded continuation, overlap, old-history gaps, lost-response/lease recovery, retries, terminal failures and unordered financial events. No actual Stripe scan ran during implementation.

Approved offer registration and **new** offer-period enrollment now require `PACKPROOF_PUBLICATION_RECEIPT_FILE` and its independently reviewed canonical `PACKPROOF_PUBLICATION_RECEIPT_SHA256`, plus the running `PACKPROOF_RELEASE_SHA`. The receipt comes from `scripts/publication-policy-gate.mjs`, matches the exact offer and approved terms, pins entity/documents/support/approval records, and expires within 24 hours. The backend validates its hash and time/offer/release binding. A still-fresh receipt from another deployment is rejected; trusted internal injection must also provide an independently expected release SHA. An existing identical period replay remains idempotent. Trusted internal test adapters can inject a synthetic receipt; HTTP callers cannot supply receipt authority. No receipt or legal approval is generated by normal capture, billing webhook or application startup.
