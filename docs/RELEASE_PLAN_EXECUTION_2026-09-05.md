### Confirmed configuration gaps to reconcile

1. **S3 permissions:** the observed API task-role inline policy permitted only `s3:GetObject`/`s3:PutObject` on the evidence bucket's `evidence/*`. Lifecycle originals and new derivatives use `proofs/*`. There were no attached task-role policies, permissions boundary or bucket policy supplying the missing grant. Add the exact required `proofs/*` resources to the API task role before enabling those paths; do not broaden to unrelated buckets or all S3 actions. Recheck actual policy after root change.
2. **Origin preservation:** `infra/deploy-staging-current.ps1` passes only the CloudFront URL as `WebOrigins`; its later optional-setting preservation skips names already present. Used unchanged, this can remove the customer-domain and Sites origins. Preserve the complete current explicit allow-list and integration/auth/secrets configuration in the candidate update. Never replace it with a wildcard.
3. **Capacity:** the candidate image includes FFmpeg/FFprobe and requires writable temporary storage. Observed 256 CPU/1024 MiB has not been validated for 200 MiB original handling plus concurrent bounded redaction. Consider a reviewed 512 CPU/2048 MiB task configuration and measure; this document does not claim that sizing passed load tests.
4. **Signing:** no signing key or IAM readiness was established by this read-only baseline. Follow [MANIFEST_SIGNING_OPERATIONS.md](MANIFEST_SIGNING_OPERATIONS.md); KMS mode uses an exact existing asymmetric key ARN and only `kms:GetPublicKey`/`kms:Sign` for the task role plus corresponding key policy. Do not substitute a test key or silently fall back from required signing to unsigned.

## Concrete migration/deployment sequence for the root integrator

The repository's `.github/workflows/deploy-staging.yml` calls `infra/deploy-staging-current.ps1` on matching `main` changes; its CI workflow is separate. Automatic deployment is disabled for this release because legacy scripts replace runtime origins/signing/capacity and can race the reviewed rollout; manual dispatch remains available for operator repair. The deploy workflow's web check looks for legacy UI strings and does not establish the new website acceptance criteria. Preserve the existing environment rather than applying `production-foundation.yaml` as a replacement database/environment.

1. Record candidate SHA and complete gates below. Build the reviewed `backend/` context with its lockfile, Dockerfile, source, OpenAPI and **all migrations 027–031** through the existing CodeBuild/ECR path. Use an immutable candidate tag/digest and verify runtime `ffmpeg`/`ffprobe` availability. `/meta` needs the matching explicit release variables; the Dockerfile does not bake a Git identity by itself.
2. Record a fresh current Express/task/environment configuration without disclosing secret values. Preserve environment entries, secret references, Cognito/integration settings, public URL, full origin allow-list, roles and rollback configuration. Take a named pre-release RDS snapshot and verify it is available before database change.
3. Reconcile the exact S3 prefix permissions and any intentionally enabled signing configuration. Keep optional features disabled until their prerequisites pass. This is a configuration update over the same canonical database and object store.
4. Run **one** migration process from the candidate image using the same database configuration, task/execution roles and current network access. Override the container command with the following; it reads the injected runtime configuration without printing credentials:

   ```sh
   node --input-type=module -e "import {loadConfig} from './dist/config.js';import {openDatabase} from './dist/db/open.js';import {migrate} from './dist/db/migrate.js';const d=await openDatabase(loadConfig());await migrate(d.db);await d.close();"
   ```

   Register/run a one-off candidate task from a copy of the current definition with `Main` image replaced, or use the deployment's equivalent isolated task. Wait for exit code zero and retain migration logs/ledger. The normal API startup also migrates before listening, and the integrated migration runner uses a transaction-scoped PostgreSQL advisory lock; do not launch competing migration/startup processes against unapplied migrations.
5. Update the existing Express service to the candidate image and preserved/reviewed configuration. Wait for deployment convergence and healthy tasks through the canary/bake window. Check `/health`, exact `/meta`, allowed-origin requests, authentication and a consented fixture exercising original commit, finalized retrieval, stage/derivative S3 storage, privacy and optional signing. 6. Deploy the matching new website contract after the API is available. Capture the actual website revision and run root's browser golden paths. Build/distribute the compatible native binary separately; stale clients cannot supply the newly required commerce capture session.

### Optional switches and rollback

The API process hosts the new workers; no new worker service is assumed. Commerce ticks every 15 seconds with bounded pages/connections and only operates opted-in active connections. Thumbnail processing is bounded and optional. A flag is a release control, not proof that a downstream provider is ready.

| Control | Purpose |
| --- | --- |
| `PACKPROOF_COMMERCE_WORKER=false` | Stop automatic commerce processing; preserve saved checkpoints and explicit seller consent. |
| `PACKPROOF_MEDIA_WORKER=false` | Stop background thumbnail processing. |
| `PACKPROOF_REPLAY_THUMBNAILS=false` | Stop new thumbnail work. |
| `PACKPROOF_REDACTION_ENABLED=false` | Stop new sensitive-media render work. |
| `PACKPROOF_RECEIPT_NOTIFICATIONS=false` | Stop receipt email dispatch. |
| `PACKPROOF_FEATURE_REPLAY/ASK/CASES/COMPARE/HISTORY=false` | Independently stop the corresponding optional actions. Existing authorized original access remains available. Set each variable separately. |

For an API rollback, use the preserved old image **digest** and preserved runtime configuration, and align or disable the new client entry points that require the candidate contract. Leave additive tables and committed originals intact; do not run destructive down migrations or overwrite finalized manifests. Rollback to the old image also restores the old capture-policy behavior, so pause new primary intake if that would reintroduce a release blocker. Keep the pre-release snapshot for an operator-led recovery decision; database restoration replaces later writes and is not an automatic routine rollback. Revalidate `/meta`, auth, CORS, existing Proof reads and queue/worker state after rollback.
