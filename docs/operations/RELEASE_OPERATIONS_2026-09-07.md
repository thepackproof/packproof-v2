# PackProof release operations — September 7, 2026

Implementation exists in source. No deployment, database certificate rotation, role grant, restore drill, branch-protection bypass attempt, native-device verification, or independent security review is asserted by this document.

## Database identity and migrations

`PACKPROOF_DB_SSLMODE=verify-full` is the default for composed URLs. Legacy `require` and `verify-ca` now also verify both certificate chain and hostname using Node TLS. Set `PACKPROOF_DB_CA_FILE` to the reviewed public RDS CA bundle mounted read-only, or inject the public certificate chain through `PACKPROOF_DB_CA_PEM`. URL `ssl=false` and certificate query parameters cannot override the configured security object. Hosted `sslmode=disable` and permissive TLS modes fail closed. A missing/malformed CA file fails startup. Obtain the current bundle from AWS, verify its published provenance, and record its SHA-256 in the deployment evidence; no private key belongs in this file.

Certificate rotation drill: provision the replacement CA alongside the current CA in an isolated environment; connect to the intended hostname, prove an untrusted CA and wrong hostname fail; rotate the test server to the replacement CA and prove the overlap bundle succeeds; remove the old CA only after every active server and client has moved. These live TLS checks remain a release gate. Never temporarily disable verification.

Migration runner: `node dist/db/migrate-cli.js` under a separate migration credential. Set `PACKPROOF_MIGRATION_DATABASE_URL` and `PACKPROOF_MIGRATION_ROLE` to its exact role name. Runtime starts with `PACKPROOF_MIGRATE_ON_START=false` and validates every migration checksum. New deployments store SHA-256 at first application. Existing rows with no checksum require a reviewed baseline against the deployed source; only that one-time migration run may set `PACKPROOF_ADOPT_LEGACY_MIGRATION_CHECKSUMS=true`. Altered applied migrations are rejected. A 15-second lock budget and advisory lock protect the bootstrap/check/apply transaction. Never edit an applied SQL file; add a forward migration.

Apply `infra/sql/runtime-roles.sql` only after checking actual table names and role ownership. The application login must not own tables or inherit migration/owner privileges. Execute runtime CREATE/ALTER/TRUNCATE attempts and committed-evidence mutation attempts in a disposable database; every attempt must fail. Backup and maintenance logins remain separate. Record role membership and denied-operation evidence before production rollout.

## Independent work and health

`PACKPROOF_PROCESS_ROLE=api` runs HTTP without scheduled processing. `worker` runs schedules and only health endpoints. `combined` remains a development/legacy transition mode and cannot issue strict protected recovery receipts. A production worker is a separate task with no public ingress. Its task health uses `/live`; load-balancer admission uses `/ready`. `/health` remains the compatibility liveness endpoint. No provider call participates in liveness, so an outage does not cause restart loops.

Runtime readiness checks database access, checksummed schema, the exact object version named by `PACKPROOF_READINESS_OBJECT_KEY` and `PACKPROOF_READINESS_OBJECT_VERSION`, and required signing trust freshness. The public endpoint omits dependency internals; the operational CLI provides details. The sentinel is a dedicated synthetic object created and pinned during deployment, never customer evidence. It must be accessible via the same storage authority used for committed originals. Readiness cannot prove every historical key is decryptable: perform the restore/integrity drills separately.

The scheduler starts independently of HTTP requests. Recovery, policy recovery, recipient exports, thumbnails, shipment/provider sync, notification delivery and billing usage reconciliation use existing domain leases/idempotency. `operational_worker_heartbeats` records worker, random instance ID, state and latest successful completion; it contains no media, addresses or raw request tokens. A hung callback is not restarted over itself. Stale heartbeat beyond two expected intervals and stale useful completion must alert. Inspect both `heartbeat_at` and `last_success_at`: repeated errors must not count as successful work. `PACKPROOF_STAGING_CLEANUP_WORKER=true` is opt-in only after its separate maintenance authority is verified. Committed/journal keys are refused by the cleanup adapter.

The operational CLI reports queue age, dead letters, pending declarations and worker freshness without record identifiers. Initial alert thresholds: preservation oldest >10 minutes; missing worker heartbeat >two intervals; any integrity/journal conflict immediately. Finalization >2% errors in 15 minutes with at least 20 attempts is a proposed metric alert requiring connected telemetry. None of these are a contracted SLA. Initial internal objectives remain 99.5% access availability, 99% eligible uploads committed within 24 hours, four-hour restore, and database RPO <=15 minutes, measured before publication.

## Recovery authority gate

Strict assurances require `PACKPROOF_REQUIRE_DURABLE_RECEIPTS=true`. Activate the sticky database policy with the migration-role CLI only after verification, then deploy API and worker with the same flag. Runtime refuses a flag/policy mismatch and cannot change the migration-controlled fence. Enable only after a dedicated journal bucket, recovery KMS key, and worker task role are independently tested. Ordinary API task roles must have no journal write or recovery-sign authority; workers must have no journal version deletion or KMS deletion permission. The journal bucket must differ from staging and committed-media buckets. The recovery key must differ from the ordinary manifest key. Split `api` and `worker` process roles are mandatory. The deployed role identities, IAM denies, Object Lock configuration, and restore fence must match a reviewed protection evidence record.

The JSON file configured by `PACKPROOF_RECOVERY_PROTECTION_EVIDENCE_FILE` is SHA-pinned by `PACKPROOF_RECOVERY_PROTECTION_EVIDENCE_SHA256`. Required fields: `schema: packproof.recovery-protection.v1`, `bucket`, `signingKeyArn`, `workerRoleArn`, `apiRoleArn`, `environment`, `reviewedBy`, `evidenceReference`, `verifiedAt`, `expiresAt`. Required true checks: `versioningVerified`, `objectLockVerified`, `conditionalCreationVerified`, `apiJournalWritesDenied`, `apiRecoverySigningDenied`, `workerDeletionDenied`, `kmsDeletionRestricted`, `restoreWriterFenceVerified`. A configuration flag is not the evidence: retain the actual IAM tests and restore drill at `evidenceReference`. The runtime validates consistency and expiry, not the reviewer's conclusions.

Set `PACKPROOF_RECOVERY_S3_BUCKET`, `PACKPROOF_RECOVERY_KMS_KEY_ARN`, `PACKPROOF_RECOVERY_TASK_ROLE_ARN`, `PACKPROOF_API_TASK_ROLE_ARN`, and explicit `PACKPROOF_RECOVERY_WRITER_GENERATION`. The generation must match the durable writer-fence row (`initial` only for an unrecovered initial database). `PACKPROOF_RECOVERY_SIGNING_ALGORITHM` defaults to ECDSA_SHA_256; retain previous trusted public keys in `PACKPROOF_RECOVERY_TRUST_HISTORY_JSON`. The worker uses its dedicated ECS credential chain. The API validates deployment evidence but never initializes the recovery signer.

## Incidents and rollback

1. Preservation conflict or missing acknowledged receipt: stop affected admission/new-write feature flags, preserve logs and exact versions, page the assigned preservation owner. Never delete a conflicting journal object or label a prepared object accepted. Fence old writers through the independent authority and database before replay.
2. Stalled exports/provider/email: inspect worker last success and domain leases, provider status and error codes. Respect retry time. Use the domain replay command after root cause repair. Never directly mark a job complete. Lost-response retries use original operation IDs.
3. Compromised credential: revoke that authority, preserve audit evidence, rotate the managed secret/key with a compatible trust record, test revoked access and permitted reads. Do not print credentials in diagnostics.
4. Failed deployment: retain the current tasks and known-good image references; revert code/flags through the reviewed deployment path, keep expanded schema and append-only history. Verify signing trust and exact originals. Android recovery requires a compatible higher version code, not installing a lower code over the current application.
5. Missing/decryption-inaccessible media: keep the affected record unavailable, inspect the exact bucket/key/version and KMS grants without substituting another object. Restore under the isolated drill and reconcile every issued/retrievable receipt across the backup boundary before reopening access.

Do not claim those human gates complete from source code alone.
